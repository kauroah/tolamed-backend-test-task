# Реализация списания бонусов

### Обеспечено:

* Используется транзакция с уровнем `SERIALIZABLE`.
* Применяется `SELECT ... FOR UPDATE` для блокировки строк пользователя.
* Баланс рассчитывается на стороне БД с использованием `NOW()`.
* Реализована защита от повторного запроса через `(user_id, requestId)`.

---

## Контракт `POST /users/:id/spend`

* `requestId` обязателен (из body или `Idempotency-Key` header).
* Приоритет у `Idempotency-Key`.
* Идемпотентность — в пределах `(user_id, requestId)`.

Ответы:

* `200` `{ duplicated: false }` — первое списание
* `200` `{ duplicated: true }` — повтор того же запроса
* `400` — недостаточно бонусов
* `409` — если requestId использован с другим payload (расширяемая логика)

# Реализация очереди

Endpoint:

```
POST /jobs/expire-accruals
```

Логика:

* Находятся `accrual` с `expires_at <= NOW()`
* Для каждого создаётся `spend` с `request_id = "expire:<accrual_id>"`
* Повторное создание исключено
* Используется транзакция с `SERIALIZABLE`
* Реализована идемпотентность обработки

# Анализ и рефакторинг

## 1. Какие проблемы были в исходной реализации списания?

Исходная реализация:

* не защищала от параллельных запросов;
* не использовала блокировки строк;
* баланс рассчитывался без транзакционной изоляции;
* отсутствовала защита от duplicate request;
* expired accrual учитывались в балансе;
* возможен отрицательный баланс.

---

## 2. Какие проблемы при одновременных запросах вы устранили и как именно?

Проблема race condition:

Два параллельных запроса могли:

* одновременно прочитать баланс;
* оба успешно пройти проверку;
* создать два списания сверх доступного баланса.

Решение:

* транзакция `SERIALIZABLE`;
* `SELECT ... FOR UPDATE` по строкам пользователя;
* расчет баланса внутри транзакции;
* повторная проверка баланса после блокировки.

Теперь только один запрос может успешно завершиться.

---

## 3. Какие обязательные правила корректности вы обеспечили на уровне БД и на уровне кода?

На уровне БД:

* Транзакции с `SERIALIZABLE`
* Row-level locking через `FOR UPDATE`
* Расчет баланса через SQL-агрегации

На уровне кода:

* Проверка идемпотентности до бизнес-логики
* Баланс не может быть < 0
* Expired accrual исключаются через `expires_at > NOW()`
* Queue операции идемпотентны

---

## 4. Как реализована защита от повторного одинакового запроса (duplicate request)?

Используется область идемпотентности:

```
(user_id, requestId)
```

Алгоритм:

1. В начале транзакции ищется существующий `spend`
2. Если найден — возвращается `{ duplicated: true }`
3. Новый `spend` не создаётся

Это гарантирует отсутствие повторного бизнес-эффекта.

---

## 5. Как обеспечено, что просроченное начисление (expired accrual) не участвует в балансе?

Баланс считается SQL-запросом:

```sql
AND (expires_at IS NULL OR expires_at > NOW())
```

Таким образом:

* просроченные начисления физически остаются в БД;
* но логически не участвуют в расчёте баланса.

---

## 6. НКак реализована надежная обработка очереди (повторные попытки, паузы, защита от дублей)?

Для обработки expire:

* Используется предсказуемый `request_id = "expire:<accrual_id>"`
* Перед созданием `spend` выполняется проверка существования
* Повторная постановка задачи безопасна
* Повторная обработка безопасна
* Реализована retry-логика (attempts + backoff)

Бизнес-эффект строго один.

---

## 7. Какие компромиссы вы приняли в рамках ограничения 4–6 часов?

В рамках ограничения времени:

* Архитектура не переписывалась полностью.
* Не внедрялся DDD.
* Не добавлялись сложные abstraction layer.
* Валидация payload минимальная.
* Не добавлялись дополнительные индексы (хотя рекомендованы для production).

Фокус был на:

* корректности;
* транзакционной безопасности;
* консистентности данных;
* покрытии тестами.
